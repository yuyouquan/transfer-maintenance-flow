## 文档目的

定义 PMS（项目管理系统）下「项目转维模块」的产品形态、入口路径、功能边界与状态机。开发与测试以本文档为唯一交付依据；文档中所有截图来自实际可运行系统（仓库见下方说明）。
> **关于代码仓库**：本模块设计阶段在两个仓库并行——`transfer-maintenance-flow` 用于跑通业务流程原型，`pms-2026` 用于沉淀 PMS 整体产品形态。最终交付为 PMS 项目内的「项目转维模块」，不存在独立的转维系统。

## 1. 背景与目标

### 1.1 背景

项目从研发阶段交付到维护阶段是研发组织内的高频动作。当前的转维交接散落在线下文档、邮件和飞书表格中：交接清单（CheckList）、评审要素、Block / 遗留任务都靠人工同步；各角色（SPM / TPM / SQA / 底软 / 系统 / 影像）的责任与状态没有结构化承载，维护团队常常拿到的是"过期的截图 + 失效的链接"。随着项目并发数增长，需要把整个转维流程电子化、可追溯、可审计，并且**作为 PMS 的一个产品模块**与项目空间深度结合，让转维状态成为项目空间的一等公民。

### 1.2 目标
> **在 PMS 中建设「项目转维模块」：以项目空间为入口承载转维流程；待办、配置、流水线、模板复用 PMS 现有壳与权限体系。**

| 维度 | 目标 |
|---|---|
| 入口收敛 | 项目转维申请、详情查看、节点操作、模板配置全部从 PMS 入口进入 |
| 上下文一致 | 在项目空间「基础信息」就能直接发起转维、查看本项目的全部转维流水线 |
| 配置统一 | CheckList / 评审要素模板版本化管理纳入 PMS 配置中心 |
| 待办统一 | 转维节点级待办（资料录入、维护审核、SQA 审核）进入 PMS 工作台待办中心 |
| 流程可追溯 | 流水线节点级历史 + 角色驳回评审意见 + Block / 遗留任务全程可查 |

### 1.3 非目标

- 本期不引入跨项目的批量转维操作
- 本期不重写 PMS 已有非转维功能（计划、需求、缺陷等）
- AI 检查规则的算法实现不在 PRD 文档约束范围内（仅约定输入输出契约）

## 2. 范围与边界

### 2.1 范围内

「项目转维模块」由以下 4 类入口 + 6 个业务视图组成，全部归属 PMS：**入口（4 处）**

- 项目空间「基础信息」中：① 申请转维按钮 ② 转维信息模块（项目维度的转维申请列表）
- 工作台「待办中心」承载转维节点级待办
- 配置中心新增「转维材料模板配置」tab**业务视图（6 个，详见 §5.3–5.8）**
- 项目转维申请页（项目锁定）
- 转维详情页（流水线、CheckList、评审要素、Block / 遗留任务、历史记录）
- 资料录入与 AI 检查页（含驳回闭环 Collapse / 二次提交确认）
- 维护审核页（逐项 / 批量 / 整角色 通过或驳回）
- SQA 审核页（通过 / 关闭流水线）
- 模板配置（CheckList 模板 + 评审要素模板的版本化管理）

### 2.2 范围外

- AI 检查规则的算法本身（仅约定接口契约）
- PMS 已有功能（计划、概况、需求、缺陷、团队等）

### 2.3 关键约束

- **整机产品项目专属**：申请转维入口仅在「整机产品项目」类型的项目空间出现
- **代码仓库分工（设计阶段）**：`transfer-maintenance-flow` 仓库提供业务流程原型与单测视图；`pms-2026` 仓库承载 PMS 完整产品形态。两个仓库均为设计与原型阶段的工作产物，最终都收敛到 PMS 主仓发版

## 3. 用户角色与权限

项目转维模块沿用以下角色定义，由 PMS 用户系统统一进行身份认证。

### 3.1 角色与关键操作

| 角色 | 关键操作 |
|---|---|
| SPM / TPM / 底软 / 系统 / 影像（研发侧） | 资料录入与AI检查、提交审核、按驳回意见修改后重新提交 |
| SPM / TPM / 底软 / 系统 / 影像（维护侧） | 维护审核：逐项 / 批量 / 整角色 通过 / 驳回（驳回时填评审意见 + Block 任务） |
| SQA | SQA 审核：通过（→ 信息变更）/ 不通过（→ 流水线终止 + 可重开） |
| 项目 SPM / 系统管理员 | 失败流水线的「重新发起转维」 |
| 申请人 | 关闭流水线（受角色审核进度限制） |

| 操作 | 项目 SPM（研发侧） | 项目 TPM | 底软 / 系统 / 影像（研发侧） | SQA | 维护团队（同角色） | 项目申请人 | 系统管理员 |

| 申请转维 | ✓ | – | – | – | – | – | ✓ |
| 录入资料（按角色） | ✓（仅 SPM 项） | ✓（仅 TPM 项） | ✓（各自角色项） | – | – | – | – |

| 提交角色资料审核 | ✓ | ✓ | ✓ | – | – | – | – |
| 维护审核（按角色） | – | – | – | – | ✓（仅本角色） | – | – |
| 整角色 通过 / 驳回 | – | – | – | – | ✓（仅本角色） | – | – |
| SQA 审核 | – | – | – | ✓ | – | – | – |

## 5. 功能详细

### 5.1 项目空间 · 基础信息 · 申请转维入口

仅在「整机产品项目」类型的项目空间「基础信息」页顶部 banner 右侧显示「申请转维」按钮，作为该项目发起转维流程的唯一入口。

> 画板/图片占位（飞书 image token: `XYWhbNo0Io64MIx1nrwcpKWonJb`）

#### 5.1.1 显示规则

| 条件 | 行为 |
|---|---|
| 项目类型 = 整机产品项目 | 显示按钮 |
| 项目类型 ≠ 整机产品项目 | 隐藏按钮（如：技术项目、产品项目、能力建设项目等） |
| 项目状态 = 已完成 / 已关闭 | 仍显示按钮（允许同一项目再次发起转维） |

#### 5.1.2 点击行为

点击按钮后，跳转到项目转维模块的「申请页」（详见 §5.4），并将当前项目的 `projectId` / `projectName` 自动填入「项目选择」字段，**该字段置为只读不可修改**。

#### 5.1.3 数据契约

- 入参：`projectId` (string, 必填)
- 出参：`transferApplicationId` (string, 申请创建成功后回填到 §5.2 的列表)

#### 5.1.4 异常

- 当前用户对该项目无「发起转维」权限：按钮显示为禁用态，hover 提示「请联系项目 SPM 或管理员发起转维」

### 5.2 项目空间 · 基础信息 · 转维信息模块

- 当前项目存在 status=`in_progress` 的进行中转维：按钮仍可点击，跳转后申请页将提示已有进行中流程并阻断提交在「基础信息」页面新增 `section-transfer` 区块，**仅当该项目存在转维申请记录（含已取消/已失败/已完成）时显示**。表格按"项目维度"列出该项目的所有转维申请；行内点击「详情」打开转维详情页（详见 §5.3）。

> 画板/图片占位（飞书 image token: `JObabRd9Zog9qfxdenAcMd80nae`）

#### 5.2.1 表格列

| 列名 | 说明 |
|---|---|
| 项目名称 | 行内显示项目名 + 项目编号；与当前项目空间的项目对齐（同一行） |
| 流水线进度 | 5 节点流水线 mini 视图（项目发起 → 资料录入与AI检查 → 维护审核 → SQA审核 → 信息变更），节点圆点反映角色级状态（含驳回回退表现） |
| 计划评审日期 | 申请时填写的目标日期 |

| 操作 | 行内按钮组：详情 / 录入 / 评审 / SQA审核 / 关闭，按申请状态与当前用户角色权限动态显隐 |

#### 5.2.2 操作按钮显隐矩阵

| 按钮 | 显示条件 |
|---|---|

| 重开 | `status=failed` 且未被重开过；项目 SPM 或系统管理员可点击 |

### 5.5 资料录入与AI检查

由 §5.2 列表行内「录入」按钮进入。仅当 `application.status = in_progress` 且 `dataEntry ≠ success` 或当前角色被驳回时按钮才出现。

> 画板/图片占位（飞书 image token: `FXhZbGRoiojU9Qx4PescfcG4nZe`）

#### 5.5.1 页面布局

| 区域 | 内容 |
|---|---|
| 顶部 | 项目名 + 角色 Segmented（多角色用户可切换）+ 流水线进度条 |
| 驳回 Collapse | 仅当当前角色存在被驳回项时显示，默认收起；展开后含「评审意见」+「Block 任务列表」 |
| Tabs | 转维材料（CheckList）/ 评审要素 — 角标显示该 tab 未完成项数（Badge） |
| 主表格 | 显示当前角色的录入项；列含交付件 / 录入状态 / AI 检查状态 / 操作 |
| 顶部右侧 | 「全部委派」按钮 + 「提交{角色}审核」按钮（含 tooltip 显示阻塞原因）+ 导入 / 导出 |

#### 5.5.2 单项录入流程

1. 点击行内「录入」→ 弹窗输入交付件链接或文本
1. 选择「暂存」→ `entryStatus = draft`，AI 检查不触发
1. 选择「确认提交」→ `entryStatus = entered`，AI 检查异步触发，`aiCheckStatus = in_progress`
1. AI 检查 1–2s 后回调，命中规则 → `passed`；否则 → `failed`（附错误说明）
1. 失败的项可重新录入；之前被驳回的项重录后 `reviewStatus` 自动回退到 `not_reviewed`，且清空 `reviewComment`

#### 5.5.3 提交审核（含驳回回填闭环）

按钮启用条件：当前角色的所有 CheckList + 评审要素项全部满足 `entryStatus = entered` 且 `aiCheckStatus = passed`。提交时，根据是否为驳回后的二次提交，弹出不同确认框：

#### 5.9.3 导入 / 导出（更新模板的主要方式）

模板内容**不在配置中心 UI 内逐条编辑**，更新通过批量导入完成。每个 tab 顶部右侧固定提供「导入」「导出」两个按钮：

| 操作 | 行为 |
|---|---|
| 导出 | 把当前选中版本的全部条目导出为 Excel（`.xlsx`），列结构与 §5.9.1 表格对应；用于线下编辑或归档 |
| 导入 | 选择本地 Excel 文件 → 解析校验 → 创建新的 `draft` 版本（同一时刻最多 1 个 draft）；如已有 draft 则提示是否覆盖 |

导入校验规则：

- 必填列不能空（检查项 / 责任角色 / 智能检查规则；评审要素模板则 标准 必填）
- 责任角色必须为 5 选 1（SPM / 测试 / 底软 / 系统 / 影像），其它值整行报错
- 序号列允许缺省，按行顺序自动编号
- 任意行解析失败 → 整次导入失败 + 显示行号 + 错误详情，不创建 draft
- 解析全部通过 → 创建 draft，引导配置员进入版本对比页面 review，再点击「发布」生效

#### 5.9.4 操作流程

1. 当前 active 版本存在 → 点击「导出」拿到 Excel 模板
1. 线下用 Excel 编辑（增 / 删 / 改条目）
1. 回到配置中心点击「导入」选择编辑好的文件 → 创建 draft
1. 在版本对比抽屉里 review 差异（新增 / 删除 / 修改）
1. 确认无误后点击「发布」→ draft 转为新 active，旧 active 转 published
1. 此后新创建的转维申请即按新模板生成 CheckList / 评审要素

interface FieldDiff {
  field: string;        // 字段 key
  oldValue: string;     // 基准版本值
  newValue: string;     // 对比版本值
}

interface CompareRow {
  key: string;
  changeType: ChangeType;
  fieldDiffs: FieldDiff[];      // 仅 changeType='修改' 时非空
  modifier?: string;            // 修改人（hover Tooltip 用）
  modifyTime?: string;          // 修改时间（hover Tooltip 用）
  // 业务字段（由 fields 定义）
  [field: string]: unknown;
}

// 调用方提供的对比计算函数
type ComputeDiff = (baseVersion: string, targetVersion: string) => CompareRow[];

## 6. 状态机与数据模型

### 6.1 流水线节点状态机

转维流水线由 5 个节点串联组成：项目发起 → 资料录入与AI检查 → 维护审核 → SQA审核 → 信息变更。每个节点取值 `not_started | in_progress | success | failed`，节点之间根据角色级状态聚合派生：

> 画板（飞书 whiteboard token: `WUA7wng3JhQvdkbXXpQcjXwvnhg`）

> 图 6.1 流水线节点状态转换 + 角色级驳回回退

#### 6.1.1 自动派生规则

| 派生节点 | 规则 |
|---|---|
| `dataEntry` | 5 角色全部 `entryStatus=completed` → `success`；任意角色 `entryStatus∈{in_progress,completed}` → `in_progress`；否则保留原值 |
| `maintenanceReview` | 5 角色全部 `reviewStatus=completed` → `success`；任意角色 `reviewStatus∈{in_progress,completed,rejected}` → `in_progress` |
| `sqaReview` | 当 `maintenanceReview` 由 `in_progress` 变为 `success` 时自动从 `not_started → in_progress` |

#### 6.1.2 角色级状态（roleProgress）

每个角色有独立 `entryStatus / reviewStatus`：

| 字段 | 值域 | 说明 |
|---|---|---|
| `entryStatus` | `not_started`、`in_progress`、`completed` | 该角色 CheckList + 评审要素 全部 `entered+passed` 即为 `completed` |
| `reviewStatus` | `not_started`、`in_progress`、`completed`、`rejected` | 全部 item `passed` → `completed`；任意 `rejected` → `rejected`；任意 `reviewing/passed/rejected` → `in_progress` |

#### 6.1.3 驳回回退（核心规则）

当某角色 `reviewStatus = rejected` 时，**视觉上**：

- 资料录入与AI检查节点圆点显示为 `rejected`（红色）— 表示资料被打回需重做
- 维护审核节点圆点显示为 `not_started`（灰色）— 表示等待研发侧修改后再次提交这一回退仅是显示层的语义还原，底层 `roleProgress` 字段不变；研发侧重新提交后，所有 item `reviewStatus → reviewing`，节点圆点回到正常推进态。
