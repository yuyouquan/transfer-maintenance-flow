# 按项目类型配置转维模板、团队与遗留任务维护

日期：2026-09-22

状态：用户于 2026-09-28 确认整体设计，并授权测试通过后提交 dev、合并 main、发布 Vercel。本文是实施依据，功能是否完成以验收记录为准。

## 1. 目标与已确认规则

1. 转维材料模板配置区分「整机产品项目」与「tOS版本项目」。整机支持 CheckList、评审要素；tOS 只有 CheckList。原来用于指代 CheckList 的「转维材料」统一显示为「CheckList」，父级名称保留「转维材料模板配置」。
2. 两类项目分别配置一套「角色名 + IPM角色Code」，每套同时作用于在研团队和维护团队，并决定各领域录入、审核与流水线角色。
3. 模板序号由用户填写，按文本保存，例如 V-01、V-02，不能用表格索引生成或转为数字。
4. 序号与标准／评审要素一一对应；一对序号与内容下允许多条类型、角色等明细。配置列表将两个分组列一起纵向合并，明细仍逐行呈现。
5. 维护 SPM 审核时可新增遗留任务、修改任意遗留任务状态。
6. 在申请详情页，维护 SPM 可以继续新增遗留任务、修改任意任务状态，审核完成不锁定此能力；任务责任人仍只能把自己未解决的任务标记为已解决。

## 2. 实现方式比较与建议

| 方式 | 优点 | 代价 |
| --- | --- | --- |
| 两类项目使用共享配置能力，申请创建时保存配置快照（推荐） | 同一份角色定义连接配置、申请、录入、审核、待办，已有申请稳定 | 需要替换现有多处固定角色映射 |
| 两类项目各自复制页面与流程 | 起步直观 | 修改需维护两套实现，权限与导入规则易发生差异 |
| 已有申请实时跟随最新配置 | 配置修改立即影响所有项目 | 可能替换进行中流程的角色、材料和审核责任人，需额外迁移机制 |

采用第一种方式。以下设计中的默认处理均属于此次整体设计的建议，尚未把它们视为用户逐项确认的要求。

## 3. 配置导航与模板隔离

```text
配置中心
└── 转维材料模板配置
    ├── 整机产品项目
    │   ├── CheckList
    │   ├── 评审要素
    │   └── 转维团队配置
    └── tOS版本项目
        ├── CheckList
        └── 转维团队配置
```

在同一配置区域通过两级页签切换项目类型和具体配置；面包屑保留完整路径。项目类型切换时重置不适用的子页，tOS 不出现评审要素入口。现有 CheckList、评审要素深链接兼容到整机产品项目。

两类项目的 CheckList 数据、版本记录和团队配置分别保存；导入或编辑只影响当前类型。评审要素只允许归属整机产品项目。

## 4. 表头与现有字段映射

CheckList 导入模板及配置表格顺序：

`序号 | 标准 | 类型 | 责任角色 | 资料录入-责任人 | 人工审核-责任人 | 智能检查规则`

评审要素导入模板及配置表格顺序：

`序号 | 评审要素 | 类型 | 备注 | 责任角色 | 资料录入-责任人 | 人工审核-责任人 | 智能检查规则`

当前代码的评审要素表没有名为「类型」的字段，实际使用「标准、说明」。为保留原数据并与用户要求对齐，建议明确如下迁移：

| 配置 | 当前字段及表头 | 调整后 |
| --- | --- | --- |
| CheckList | checkItem／评审要素 | 标准 |
| CheckList | type／类型 | 类型，移到标准之后 |
| 评审要素 | description／说明 | 评审要素 |
| 评审要素 | standard／标准，现有值如项目管理、文档归档 | 类型，移到评审要素之后 |
| 两类材料 | 配置页自动生成行号 | 用户填写的文本序号 |

其余列顺序及原内容保留。编号只是业务展示和分组字段；内部明细 ID 保持独立，不能把 V-01 当作每条明细的唯一 ID。长文本继续支持全文查看。

### 分组与导入规则

- 一一对应约束限定在同一项目类型、同一材料类别、同一模板版本内。不同项目类型可各自使用 V-01。
- 一组可以包含多条类型、角色、资料录入责任人、人工审核责任人和智能检查规则不同的明细。
- 同一编号对应不同标准／评审要素，或同一标准／评审要素对应不同编号，导入校验失败并指出行号。
- 支持 Excel 真实纵向合并单元格，并将合并区域的编号和内容还原到每条明细；也支持逐行重复填写同一对编号与内容。未处于真实合并区域且未填写分组信息的行报错，不盲目沿用上一行。
- 编号按文本原样保留前导零和连字符；要求非空，不擅自限定只能使用 V 前缀。
- 保留文件中组首次出现的顺序和组内明细顺序；相同分组合并呈现。搜索后仅展示匹配明细，重新计算跨行范围；分页不拆开分组。
- 解析、字段或角色校验失败时，当前有效模板和版本保持不变。校验成功后显示分组数、明细数，确认导入后生成新版本；导出与下载模板使用同一字段顺序。
- 模板的责任角色及录入／审核角色引用均校验到本项目类型的团队配置，避免生成无人承担的项目项。

## 5. 团队配置与申请快照

团队配置列表提供新增、编辑、删除，业务输入字段为「角色名」「IPM角色Code」。内部维护稳定角色 ID，避免重命名破坏历史引用。角色名与 Code 必填且在同类项目内唯一；被当前有效模板引用的角色不能直接删除，需先调整模板。

同一套角色同时生成左右两侧的在研、维护人员槽位。按 IPM角色Code 匹配项目原团队人员，未匹配到的槽位保持待选，不任意指派人员。角色标签采用配置的角色名，人员归属通过角色 ID 与用户 ID 表达，避免把用户本身的默认岗位当作申请中的角色。

维护 SPM 最终审核仍需明确责任人。建议保留当前 SPM 系统角色身份、使用稳定 ID 标识其最终审核职责；该角色允许编辑显示名和映射 Code，但不允许删除。新增普通角色只参与领域录入／审核，不因名称与 SPM 相似而获得最终审核权限。

每个新申请保存项目类型、所用模板版本、团队角色快照、双方选定成员。详情、录入、领域审核、最终审核汇总、流水线和待办从该申请快照读取角色与责任人。后续配置变更只作用于新申请。

有模板任务的录入／审核槽位，以及维护 SPM 槽位必须选人后才能提交。未配置任何有效 CheckList 时不可发起申请。已配置但无材料任务的角色可出现在团队配置中，页面显示无待处理项，不作为未完成项阻塞流程。

tOS 申请仅生成 CheckList，录入、审核、详情、最终审核及导航均不出现评审要素区块，状态汇总也不等待评审要素。旧申请保留原角色和材料状态，补充整机类型兼容值。

重新发起按对应项目类型的当前配置创建新快照。旧录入内容只能按明确、唯一的明细对应关系回填；不能仅按编号或标准覆盖整组多条明细。匹配存在歧义时保留旧申请，新的相应明细要求重新录入。

## 6. 遗留任务交互与权限

维护 SPM 审核页和申请详情页共用遗留任务列表与新增表单。新增字段沿用现有业务内容：责任人、部门、任务描述、截止日期；新增默认「未解决」，创建时间自动记录。

状态沿用已有枚举「未解决」「已解决」「已取消」。维护 SPM 可在三个状态之间修改，包括重新打开；不扩大为编辑已创建任务的描述、责任人等其他字段。

| 用户与页面 | 新增 | 修改状态 |
| --- | --- | --- |
| 当前申请维护 SPM，维护 SPM 审核可操作期间 | 可以 | 该申请所有遗留任务的三个状态均可切换 |
| 当前申请维护 SPM，申请详情 | 可以 | 该申请所有遗留任务的三个状态均可切换；不受最终审核结果限制 |
| 遗留任务责任人，申请详情 | 不可以 | 仅本人任务：未解决 → 已解决 |
| 其他用户 | 不可以 | 不可以 |

判断维护 SPM 依据申请快照中的实际成员 ID；全局岗位或管理员标识本身不代替此任务职责。责任人也按用户 ID 识别，兼容旧 mock 任务仅存姓名的记录。

按钮显示和状态写入入口使用一致的权限判断。切换用户后，已打开的弹窗保存时重新校验，防止沿用原用户权限。仅修改本申请任务。任务变更不会改变流水线的已通过／未通过结论。

新增和维护 SPM 状态修改记录操作者、任务、前后状态到申请历史。保存后审核页与详情页读取同一份任务数据。

代码核对发现领域审核页的「通过并创建遗留任务」目前仅写提示与历史，没有保存任务。本次共用遗留任务能力时一并接入实际任务写入，使这些任务可供维护 SPM 后续处理。

## 7. 代码边界与运行约束

- 新增共享配置状态与模板解析／分组模块；配置页使用统一的数据源，替换当前模拟导入成功与静态导出提示。
- 调整 ApplicationContext 的材料生成、重开和进度计算；替换申请、工作台、流水线、录入、审核、详情中的固定五角色映射。
- 提取共用遗留任务列表／表单与权限函数，供审核及详情使用。
- 本仓库为无后端 Mock 原型。新增配置随前端共享状态在页面间生效；本设计沿用目前的运行模型，刷新会恢复 Mock 初始数据。真实 IPM Code 与成员数据需由实际 IPM 数据源提供，演示样本不冒充真实 Code。
- 当前仓库没有 PMS 项目空间实现。这里完成承接项目 ID／类型的申请流程与两类项目演示；PMS 项目空间真实入口不能仅凭此仓库页面完成验收，需要在所属 PMS 仓库核对接入点。
- 整机示例沿用现有真实字段内容和原明细 ID。tOS 新增独立的、明确为演示的 CheckList／团队／项目样本，用于验证没有评审要素时的流程，不将整机模板直接视为正式 tOS 模板。
- 工作在当前 dev 上，只提交此次任务文件；现有 diagrams、测试文档及截图脚本修改保留。用户已于 2026-09-28 授权测试通过后合并主干并发布 Vercel；不包含外部飞书文档写入。

## 8. 验收

1. 两种项目类型分别展示对应配置子页，数据和模板版本相互隔离；旧链接可用。
2. 下载模板、真实导入、导出回读：表头顺序准确，V-01 等文本编号保留，分组一一对应，真实合并区域可还原，非法输入不覆盖有效模板。
3. 同编号与内容下的多条明细在搜索、分页后仍正确配对合并，不丢失明细或原始内容。
4. 配置新增角色后创建申请，两侧团队、录入、审核、流水线与待办都出现该角色；无任务角色不阻塞，有任务缺人不能发起。
5. 新建 tOS 申请，从录入、领域审核到维护 SPM 审核通过全程仅使用 CheckList。
6. 修改配置后，已创建申请的角色、模板和成员不被替换；重新发起时分组明细回填不会串项。
7. 维护 SPM 审核与详情页新增／改状态同步，审核完成后详情仍可操作；责任人只能解决本人任务，其他人及用户切换后的旧弹窗无法越权写入。
8. 领域审核登记的遗留任务在详情及维护 SPM 审核可见；任务变更不重开或改变流水线结果。
9. 保留原委派语义与原责任人显示，覆盖只被委派人员和本人角色加委派的场景。
10. 完成类型检查、ESLint、生产构建、聚焦规则测试和浏览器具名流程验证，并检查运行时错误。生产发布若后续授权，再核对远端提交及线上行为。
